# Milestone 3: First terrain

The goal from `fovea-plan.md`: the compiler builds a small KHSV database (3DEP elevation, NAIP imagery, levels of detail), and the runtime streams it at a locked 60 Hz. Real ground under the CIGI eyepoint of milestone 2, replacing the reference grid.

As before, each step is its own pull request. Steps 1 to 4 run in WSL and CI; steps 5 to 7 need the Windows machine for the display.

## The data (checked 2026-11-06)

For a first area of about 20 x 20 km around KHSV (34.55-34.72 N, 86.90-86.65 W):

- **Elevation, 1 m:** USGS 3DEP lidar DEMs cover it, from several projects (2019 North Alabama, 2020 17-County, 2023-24 11-County). GeoTIFFs in 10 x 10 km tiles, NAD83 / UTM zone 16N, heights NAVD88 (orthometric). Listed by the TNM Access API (`tnmaccess.nationalmap.gov/api/v1/products`, dataset "Digital Elevation Model (DEM) 1 meter"); files on the public `prd-tnm` store. About 38 tiles across the projects in the box, 8-321 MB each.
- **Elevation, backdrop:** 3DEP 1/3 arc-second (about 10 m), the 1 x 1 degree tile `n35w087` (about 470 MB).
- **Imagery:** USDA NAIP, from the Microsoft Planetary Computer STAC (collection `naip`, free, no account): **2023 at 0.6 m** (newest), 2021 at 0.3 m, 2019 at 0.6 m; 20 quarter-quad COGs per year over the box, RGB + near-infrared, NAD83 / UTM zone 16N.
- **Vertical datum:** NAVD88 heights become ellipsoid heights with NOAA's GEOID18 (h = H + N), published as grids by NGS and available to PROJ.
- **Volume:** about 1.6 GB of 1 m elevation and 4.4 GB of 0.6 m imagery uncompressed for 20 x 20 km; the compiled database is smaller (compressed textures).
- All US Government works (public domain), with credits requested; `ATTRIBUTION.md` lists each.

## Decisions (accepted 2026-11-06, in `decisions.md`)

- **D-015 Tiling: a geographic quadtree.** Tiles split latitude and longitude in half at each level from two root tiles (east and west hemispheres), so the scheme covers the whole Earth and matches how sources are indexed. Each tile holds a square grid of heights (for example 257 x 257, edges shared with neighbours) and an imagery texture, with vertices relative to the tile's own ECEF origin (camera-relative on the GPU, as now). The alternative, UTM grids, is simpler for one small area but has seams between zones.
- **D-016 Level of detail: chunked quadtree by screen-space error.** Each frame, a tile splits into its four children when its geometric error would show as more than about a pixel on screen. Cracks between levels are hidden with skirts. Popping as tiles change level is measured on the desk; if it shows, morphing between levels follows (CDLOD-style). Clipmaps are the alternative: smooth, but harder to mix with the paging of mixed-resolution sources.
- **D-017 Imagery: compressed GPU textures with full mip chains, the format chosen per database.** BC7 (sRGB, about 1 byte per texel, 3-4 MB per km² of 0.6 m imagery with mips) by default; BC1 (half the size, blockier up close) and uncompressed RGBA8 as options. The compiler takes it as a build setting, the manifest and each tile's layer header record it, and the runtime reads whichever it finds, so one database can even mix them by region. Encoders from a pinned library (chosen in step 4, licence checked).
- **D-018 Database: a manifest and one file per tile.** `manifest.toml` names the schema version, the area, the layers and the sources; each tile is one binary file with a small header (magic, schema version, tile key) and a table of named layers (elevation, imagery; later materials, placements, lights), so new layers don't need a rebuild of the rest (foundational decision 2). The simulation industry's own standard, OGC CDB, was considered: it covers far more (models, features, many levels) but assumes a large toolchain; a CDB importer or exporter can come later (#33).
- **D-019 The compiler runs on Linux (WSL, CI).** GDAL is the compiler's only big dependency: on Ubuntu 24.04 it is one package (`libgdal-dev`, GDAL 3.8.4); on Windows it means building GDAL and PROJ through vcpkg or a conda environment. Databases are plain files that any runtime reads, so a Windows compiler isn't needed to fly on Windows; it can follow if wanted.
- **D-020 Heights in the database are ellipsoidal (WGS-84),** converted from NAVD88 by the compiler with GEOID18. The database also carries the geoid height over its area, so the runtime converts host sea-level altitudes properly there (issue #19).

## Step 1: Sources and fetching

- `data/sources/khsv.toml`: the area, and for each layer its source, product, year and priority. `tools/fetch-sources.py` lists the files through the TNM API and the Planetary Computer STAC, downloads them into the git-ignored `data/`, and checks sizes and hashes into a lock file that is committed. `ATTRIBUTION.md` lists each source and its credit.
- **Done when:** a fresh clone fetches the KHSV sources with one command, and a second run downloads nothing.
- **Result:** `python3 tools/fetch-sources.py data/sources/khsv.toml` (standard library only) fetched 49 files, about 15 GB, in 10 minutes: 27 1 m DEM tiles from four 3DEP projects (5.7 GB), the newest 1/3 arc-second tile (n35w087, 2026 edition), 20 NAIP 2023 quarter-quads (8.2 GB; four-band, so larger than the 4.4 GB estimate), and GEOID18 (`us_noaa_g2018u0.tif`, 16.7 MB). `data/sources/khsv.lock.json` (committed) pins each file's URL, size and SHA-256. A second run downloads nothing; `--verify` re-hashes everything (a byte changed in one file was found and re-downloaded); `--update` asks the services again, and a file whose hash changed upstream is an error until accepted. The services' occasional HTTP 500s are retried. `ATTRIBUTION.md` credits each source.

## Step 2: The database format and its reader

- `libs/terrain`: tile keys and the quadtree (geodetic bounds, neighbours, parents), the tile file format (D-018) with a writer and a reader, and a `TerrainQuery` over a database: height at a point (bilinear in the finest loaded tile) and ray intersection.
- **Done when:** tests round-trip tiles through files, reject damaged ones, and answer height and ray queries on synthetic databases exactly; no GDAL, no Vulkan.
- **Result:** `fovea/terrain/tile_key.hpp` (the quadtree: bounds, the tile at a point, parent, children, neighbours across the antimeridian), `tile_file.hpp` (the tile file: a 32-byte header, a 48-byte entry per named layer with its CRC-32, 8-byte-aligned data; the elevation layer as a float32 grid of ellipsoid heights, south-west first, edges shared; atomic writes), and `database.hpp` (`manifest.toml`, `tiles/<level>/<x>/<y>.fvt`, and `DatabaseTerrain`: height from the finest tile that reads cleanly, falling back to coarser ones and listing the problems; rays marched in half-height steps and bisected to a millimetre). Tests on synthetic databases written by the same code: a tilted plane comes back to 0.2 mm (float32) from either level, a damaged fine tile falls back to the coarse one and is reported, rays onto flat terrain match the exact ellipsoid intersection to a centimetre, and a ridge blocks the line of sight. A planted bug in the bilinear weights, the level order or the checksum check each fails a test. The review then found: test databases written into the working directory (and so committed once; now under the temp directory), a tile write that checked the stream before closing it (a full disk could have renamed a short file into place), an unbounded ray march (now stopped when it leaves the tiles, and capped), a disk read under the cache's lock, a grid size narrowed before its range check and not compared with the tiles, NaN and wrapped longitudes, points on the database's north and east edges, an unescaped name and non-atomic manifest write, and a manifest without the layers and sources D-018 lists; each fixed, with a test.

## Step 3: The compiler: elevation

- `apps/fovea-compiler` (GDAL): mosaics the 1 m projects (newest first) over the 10 m backdrop, converts NAVD88 to ellipsoid heights (GEOID18), resamples into each tile's grid at each level, and records each tile's geometric error for D-016. Writes the database.
- **Done when:** compiled heights match the source DEM (through GDAL, independently) within a stated tolerance at sampled points, including across tile edges; KHSV's field elevation comes out where published.
- **Result:** `fovea-compiler data/compile/khsv.toml` builds `data/db/khsv` (git-ignored) in 17 s on 16 threads: levels 12 to 16, all descendants of the 30 level-12 tiles touching the area (10,230 tiles of 257 x 257, 2.6 GB). The settings (`data/compile/khsv.toml`, committed) list the sources newest first by file pattern, and name any fetched file no pattern covers. The finest level (about 1.2 x 1.0 m between samples) samples the sources bilinearly between pixel centres, from the highest-priority source with all four pixels around the point (the 1 m projects, 2024 to 2017, then the 1/3 arc-second DEM), and adds GEOID18; each coarser level is filtered from the one below ([1 2 1] / 4 both ways, reading the neighbours' children across tile edges, extrapolated linearly at the database's outer edge), and each tile records its geometric error against its children plus theirs (up to 8.2 m at level 15, 38.6 m at level 12). A failed build leaves nothing; an older database is replaced, a directory that isn't one is not.
- **Checked** by `tools/check-elevation.py`, which reads the sources through GDAL's Python bindings and the tiles with its own decoder: at 6,000 points over the whole database, the finest level is within 2.7 cm of the sources at the 99th percentile (RMS 1.0 cm; at most 0.45 m, on a bank rising 6 m per metre, where interpolating the 1 m grid again at 1.2 m spacing costs that much), from either tile on tile edges; neighbouring tiles' shared samples are identical at every level (every pair at levels 12 to 15, 2,000 tiles at 16); every coarse tile is within its recorded error of the finest level; and the FAA's surveyed elevations of KHSV's four runway ends come out within 1-2 cm (NAVD88: the database less the geoid), the field elevation (628.9 ft, the highest point of the runways) within 3 cm. Unit tests (`fovea_compiler_tests`, in CI) build databases from synthetic GeoTIFFs whose heights are planes, so every sample has an exact answer: source priority (including a hole in the newest DEM and a source with a different no-data value), the geoid in 0-360 longitudes, coarse levels, shared edges on rough ground, error bounds, the reader on the result, and failures. A planted wrong geoid sign or reversed priority each fails tests; the filter's weights aren't pinned (a box filter also keeps planes exact).
- **Found on the way:** GDAL's warp (first used for sampling) gave neighbouring tiles different values on their shared edge wherever a source ended near it: by up to 25 m for cell averages, a few centimetres for bilinear, as its handling of a source's edge depends on where the warped raster starts. Sampling the sources directly, and filtering the coarse levels from the finest, made the edges identical.
- **Review:** fixed: an output path ending in "/" put the build inside the database it then replaced (and so deleted); replacing deleted the old database before moving the new one in (now moved aside, then removed, and a leftover from an interruption is refused); a source's scale, offset or units were ignored (now anything but metres is refused); a sample exactly on a source's last pixel centre was taken from the next source; the geoid's CRS wasn't checked and its longitudes were shifted once rather than wrapped; the child-tile cache was bounded by count, not size (samples now up to 1025); two spellings of a source directory counted twice; and CLAUDE.md's dependency rule now names GDAL's exception. Not changed: the cache's hit rate (the coarse levels take 3.7 s of the 17 s). Also left, wrongly: a source was skipped when `OCTTransformEx` returned false, taken then to mean no point transformed; GDAL 3.8 returns false when any point fails (step 4's review reproduced it), so one failing point dropped a source's good ones. Fixed in step 4: each point's own flag decides.
- **Not yet:** the sources' NAD83(2011) coordinates and ellipsoid are taken as WGS-84, which they differ from here by about a metre horizontally and vertically: a host flying WGS-84 ellipsoid heights would be about a metre off over this database, one flying sea-level altitudes (converted with the same geoid, #19) would not. The geoid height layer D-020 describes comes with #19. The compiler runs on Linux only (D-019).

## Step 4: The compiler: imagery

- NAIP mosaicked, reprojected into each tile's texture, colour-balanced across the quarter-quads only if seams show, mipmapped and BC7-encoded.
- **Done when:** tiles decode back to the source imagery within a stated error (PSNR), with no seams at tile edges.
- **Result:** `fovea-compiler` adds an imagery layer to every tile when the settings have an `[imagery]` table: 512 x 512 texels per tile at every level (0.6 x 0.5 m at level 16, NAIP's own 0.6 m), sRGB, with the full mip chain, in the format the settings name (BC7 by default, BC1 or RGBA8; the manifest and each tile's layer record it, D-017). The finest level samples the sources at each texel centre, bilinear between pixel centres, from the first source pattern covering it and, among one pattern's files (one year's quarter-quads, which overlap by about 300 m), the file the point is deepest inside, so the mosaic's seams fall midway through the overlaps. Each coarser tile is its four children's halves, each texel the average of four in linear light, as is each mip. Texels coarser than 1.5 source pixels are refused (they would alias; nothing averages a texel's area from the sources). KHSV: 10,230 tiles in 2 min 51 s on 16 threads (BC7 encoding is most of it), 3.6 GB, the database 5.9 GB with the elevation. The NAIP files fetched for step 1 covered the area but not the whole database (the 30 level-12 tiles reach about 1.5 km further north), so `fetch-sources.py` takes a layer `extent`, and the imagery layer now asks for the database's extent: 5 more quarter-quads (2.2 GB), 25 in all. No colour balancing: a mosaic of the whole database shows no seams on land between quarter-quads flown on different days; on the Tennessee River, sun glint on the water differs between flights, which balancing wouldn't fix.
- **Encoders:** [bc7enc_rdo](https://github.com/richgel999/bc7enc_rdo) (Rich Geldreich): `bc7enc.cpp` for BC7 (modes 1, 5, 6 and 7, perceptual error), `rgbcx` for BC1, `bc7decomp` to decode, all MIT or public domain at the builder's choice; pinned by commit and SHA-256 (no releases), built only with the compiler. Not used from that repository: `bc7e.ispc` (Apache-2.0, better but needs the ISPC compiler) and its bundled `ispc.exe`. Considered: Intel's ISPC Texture Compressor (MIT, needs ISPC), AMD's Compressonator (heavy), and Basis Universal (Apache-2.0, built around its own transcodable format).
- **Checked** by `tools/check-imagery.py`, which reads the sources through GDAL's Python bindings and builds its own reference for each tile (the rule above, in numpy), reads tiles with its own reader, and decodes BC7 and BC1 with Pillow's decoder rather than the encoder library's. On 150 random level-16 tiles BC7 comes within 44.2 dB PSNR of the reference (mips 1 to 9 at 40.3 dB or better); every tile under the middle root at levels 15 to 12 within 44.3 to 42.0 dB; each tile's outermost texels within 0.3 dB of the three rings inside them at every level (no seams at tile edges); and the texture is in place (the reference moved half a texel either way matches at least 3.6 dB worse). A small RGBA8 build matches the reference exactly (infinite PSNR), so the compiler and the checker agree on every texel; planted bugs (texel centres on corners, children in the wrong quarters, averaging in sRGB rather than linear light, a half-texel shift under BC7) each fail it. Unit tests build from synthetic RGB GeoTIFFs: a gradient patch whose bilinear values are exact pins texel centres and row order to within rounding; solid colours pin the pattern priority and the seam midway through an overlap (including at the coverage's edge, where the files tie and the other axis decides); coarse tiles are their children's halves texel for texel; BC7 and BC1 stay close to RGBA8; the layer and manifest round-trip and refuse damage; and missing coverage, too-coarse texels and non-RGB sources fail. Planted bugs (a half-texel shift, rows from the north, children swapped, sRGB averaging, priority ignored, no tie-break) each fail a test.
- **Review:** fixed: a source was skipped when any one point failed to transform (GDAL's return value, as in step 3's elevation, fixed there too); the too-coarse check counted sources no texel takes (a finer source hidden under NAIP was refused); an elevation pattern took files from imagery's patterns, silently (each layer now takes only from its own patterns); every thread reported the same bad source (now once); the subtrees started one level below the roots, however few tiles that gave the threads, and kept every one's half image (now from the first level with four tiles per thread, the roots' halves not kept); the elevation pass kept its own copy of the thread pool (it now uses the imagery's); the checker listed sources with other wildcard and path rules than the compiler; and a tile without full coverage read all its windows before failing. Each tested where a test could show it (the transform failure needs a source CRS that fails within a tile; GDAL's behaviour was reproduced instead). Not changed: the imagery pass reads back and rewrites each tile the elevation pass wrote (about 3 GB more I/O, a few seconds of the 3 minutes; building both layers in one pass would tie their levels' orders together).

## Step 5: Drawing terrain

- The renderer draws loaded tiles: meshes generated from each tile's height grid on the GPU, textured, camera-relative, with skirts; tiles chosen each frame by screen-space error (D-016). All tiles of the small area loaded up front for this step. The reference grid stays available for tests.
- **Done when:** golden images of fixed views over KHSV match in CI (lavapipe), and on the desk the terrain lines up with known landmarks (the runways) seen from the CIGI eyepoint.
- **Changed:** CI can't have KHSV (databases aren't committed, D-018, and its sources are 17 GB), so CI's checks draw databases the tests write: imagery whose colours change at known coordinates, and a golden image of hilly terrain. KHSV is drawn locally and on the desk.
- **Result:** `[terrain] database` in a config loads every tile up front (`max_level` caps it) and the renderer draws it in every view over the reference scene's sky and grid (`libs/render/src/vk/terrain.cpp`, `shaders/terrain.slang`). Each tile is an instance of one shared grid of (samples + 2)^2 vertices, the outer ring its skirt; the vertex shader reads the tile's heights (an R32F image) and raises the ellipsoid point under each sample along the ellipsoid's normal, the ellipsoid points bilinear in a 9 x 9 grid of control points the CPU computes in double relative to the tile's origin (under a centimetre from the true ellipsoid: a level-12 cell's sag is 7 mm). Tiles are placed relative to the eye on the CPU each frame, so the GPU sees only small offsets (camera-relative floats, as architecture.md requires). Heights and imagery are bindless arrays of images, indexed by tile; the imagery's own format (BC7, BC1 or RGBA8, D-017) is uploaded as is. Each frame each view picks its tiles on the CPU (`terrain_lod.hpp`: from the roots down, a tile splits where its recorded error would show as more than `pixel_error` pixels, 1 by default, D-016; tiles outside the view are left out; no allocation) and draws them all as one instanced, indexed draw, with a reverse-Z depth buffer. Skirts hang the tile's error plus its parent's plus a metre: the most a crack between neighbouring levels can open. Lighting is the photograph's own, with a little relief from a fixed sun. KHSV: 10,230 tiles, 6.3 GB, load in 29 s on lavapipe; the renderer now depends on `libs/terrain` (architecture.md).
- **Checked:** unit tests of tile selection on a real quadtree over KHSV (tiles picked cover every visible finest tile exactly once, none with an ancestor; each one that could split shows at most the pixel error; looking up picks none; a looser error picks fewer); GPU tests on written databases, under validation: four colours meeting at a known point on flat ground show within 3 px of where the view's own matrix, in double, puts it (looking straight down), and on ground rising 1 in 10 seen at 45 degrees (where ignoring the heights would put it more than 20 px off); damaged tiles are skipped and listed, a parent with a missing child is drawn whole, and `max_level` stops loading; and a golden image of hills (`tests/data/golden/terrain_hills.png`, lavapipe). Planted bugs (texture rows from the north, heights ignored, columns from the east) each fail all three image tests. A headless render of KHSV from 300 m south of runway 36L shows the runways ahead where they belong.

## Step 6: Paging

- A paging thread loads tiles from disk and uploads them on a transfer queue, from requests the render thread pushes (predicted from the view's motion); the render thread draws what's resident and never waits (architecture.md). Memory budgets, eviction, and per-frame stats (tiles resident, uploads, misses).
- **Done when:** a flight over the whole area (the test host) keeps 60 Hz with no missed frames, and no frame shows a missing tile where a coarser one could be drawn.

## Step 7: Hardware check

- Fly the scripted routes over KHSV on the desk: frame timing, paging stats, popping between levels, and the look from low altitude. Results recorded; anything unexpected becomes an issue.
